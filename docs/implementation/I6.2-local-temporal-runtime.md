# I6.2 — Validation du runtime Temporal local de développement

Date : 26 juillet 2026

## Périmètre

I6.2 vérifie le runtime Temporal installé explicitement par l'utilisateur avant I7. Il ne télécharge rien, n'utilise pas Temporal Cloud, ne lance aucune mission Codex et ne consomme aucun token. Il ne livre ni gestionnaire de binaire, ni supervision, ni backup/restore, ni upgrade, ni packaging de production I10. `temporal server start-dev` reste strictement un outil de développement.

La configuration commune aux API, worker et CLI est :

```bash
export NODRA_DATA_ROOT="$PWD/data/dev"
export NODRA_DATABASE_FILE="$NODRA_DATA_ROOT/nodra.db"
export NODRA_TEMPORAL_ADDRESS="127.0.0.1:7233"
export NODRA_TEMPORAL_NAMESPACE="nodra"
```

Le serveur de développement persiste son propre store, distinct du SQLite métier, dans `$NODRA_DATA_ROOT/temporal/dev-server.db`. L'adresse est validée comme loopback et le port provient de `NODRA_TEMPORAL_ADDRESS`.

## Procédure reproductible

Terminal 1 :

```bash
npm run temporal:dev
```

Cette commande exige `temporal` déjà présent dans `PATH`, affiche sa version et lance :

```text
temporal --disable-config-file --disable-config-env server start-dev
  --headless --ip 127.0.0.1 --port <port>
  --namespace nodra
  --db-filename <data-root>/temporal/dev-server.db
```

Elle n'installe ou ne télécharge jamais Temporal. `Ctrl-C` arrête le processus. Le mode headless évite un second port UI; les ports internes HTTP/metrics restent les ports libres choisis par le dev server.

Terminal 2 :

```bash
npm run temporal:health
npm run db:setup -- "$NODRA_DATABASE_FILE"
npm run dev
```

Terminal 3 :

```bash
npm run worker
```

Terminal 4, pour la CLI partageant exactement la même configuration :

```bash
npm run cli -- health
npm run cli -- temporal:dispatch
npm run cli -- temporal:reconcile
```

`temporal:health` échoue avec un exit code non nul si la CLI est absente, si le serveur est injoignable ou si le namespace `nodra` manque. `components.workflow.status` vaut `ok` uniquement après le probe gRPC serveur puis `describeNamespace`. Cela ne prétend pas prouver qu'un worker poll la task queue : le POC réel ci-dessous apporte cette preuve.

## POC opt-in réel

```bash
NODRA_TEST_TEMPORAL_RUNTIME=1 npm run test:poc:temporal
```

Le harness :

- choisit un port loopback libre et un data root temporaire ;
- lance le binaire `temporal` installé avec un store SQLite Temporal explicite et le namespace `nodra` ;
- vérifie qu'une adresse sans serveur est une erreur, puis que serveur + namespace donnent un workflow health vert ;
- migre un SQLite métier temporaire, démarre le vrai `TemporalMissionWorker` et exécute les Workflows/Activities I3–I6 ;
- utilise uniquement `DeterministicProvider`, défini dans `poc/temporal/`, sans processus Codex ni réseau provider ;
- prouve start, événements Activity, terminal `SUCCEEDED`, crash après acceptation Temporal avant publication outbox, inbox sans doublon, arrêt du worker, redémarrage, reconciliation, même parent au redispatch et terminal après reprise ;
- arrête le worker et le serveur, ferme les connexions et supprime tous les fichiers temporaires dans un `finally`.

Un échec laisse le log du serveur disponible seulement jusqu'au nettoyage du harness et retourne un exit code non nul. Pour une investigation persistante, utiliser la procédure dev manuelle et ses logs de terminal.

## Frontière I10

Cette validation macOS du binaire déjà installé ne satisfait pas la matrice de `12-packaging-backup-poc.md`. Elle ne valide ni distribution multi-OS, checksum/install, backend de production, supervision, crash-loop, backup/restore, upgrade ou désinstallation. Ces sujets restent I10.
